# Part 3. 가용성, DB, 관측

## 12. ALB

ALB는 HTTP/HTTPS를 보고 Target Group으로 보낸다. Listener가 포트를 받고, Listener Rule이 경로와 Host로 나누고, Target Group이 대상을 모은다. Health Check가 빠지면 그 대상으로 보내지 않는다.

예: `/api/*`는 API 그룹, `/admin/*`는 관리 그룹. 각 그룹 뒤의 EC2는 여러 AZ에 둔다.

Health Check 예:

```text
GET /health
HTTP/1.1 200
{"status":"UP"}
```

상태 판단에는 응답 코드, 타임아웃, 연속 성공·실패 횟수가 들어간다. Unhealthy의 첫 확인은 경로, 포트, 응답 코드다.

`describe-load-balancers`와 `describe-target-groups`는 계정 없이 호출하지 않았다. 로컬에서는 `poc3-operations/simulator.py`가 정상 대상만 라운드 로빈한다. `EC2-C`는 `healthy=False`라 6번 모두 `EC2-A`, `EC2-B`만 나왔다.

이전 네트워크 실습의 `네트워크/scripts/lab_lb.py`가 8001과 8002를 나눈 것과 같은 층의 동작이다. ALB는 거기에 헬스 체크와 여러 AZ가 더해진다.

## 13. Auto Scaling

Min은 최소, Desired는 유지할 수, Max는 최대다. 예시 범위는 2, 2, 4다.

시뮬레이터 정책은 CPU가 70보다 크면 Desired를 1 늘리고, 30보다 작으면 1 줄인다. 범위 밖으로는 나가지 않는다.

```text
CPU=85% desired=3
CPU=90% desired=4
CPU=50% desired=4
CPU=20% desired=3
```

50%에서는 목표를 유지하므로 4가 남는다. 20%에서는 3까지 줄고, 최소 2 아래로는 더 줄지 않는다. 최대 4에서는 더 늘지 않는 것도 코드가 검사한다.

실제 ASG에는 시작 시간, 워밍업, 쿨다운이 있다. 정책 종류는 Target Tracking, Step, Scheduled, Predictive다. CPU만 보지 않고 요청 수, 지연, 큐 길이도 지표가 된다. `describe-auto-scaling-groups`는 호출하지 않았다.

## 14. RDS

애플리케이션은 TCP 5432로 RDS Security Group을 지나 PostgreSQL에 닿는다. 스토리지는 AWS가 관리하는 블록 저장이다.

DB Subnet Group은 배치할 서브넷, Security Group은 포트, Multi-AZ는 가용성, Read Replica는 읽기 확장, Automated Backup은 복원, Parameter Group은 엔진 설정이다. Multi-AZ와 Read Replica는 목적이 다르다.

로컬 접속 시도:

```text
psql -h 127.0.0.1 -p 5432 -U study -d studydb
psql: connection to server at "127.0.0.1", port 5432 failed: timeout expired
```

`study` 데이터베이스로의 접속은 확인하지 못했다. `describe-db-instances`도 자격 증명이 없다. 실제 RDS는 엔드포인트, 인증, TLS, Security Group, 서브넷 경로가 더 필요하다.

## 15. CloudWatch

Metrics, Logs, Alarms 세 갈래다.

| 이 머신에서 쓴 것 | AWS에서 대응 |
|---|---|
| 프로세스 CPU 한 장면 | EC2 CPU 메트릭 |
| 없는 `journalctl` | CloudWatch Logs로 보낼 대상 |
| 진단 스크립트의 PASS/FAIL | 알람의 OK/ALARM |
| `df` | 디스크 사용률. 기본 EC2 메트릭에 보통 없고 Agent가 필요하다 |

메모리와 디스크 사용률은 기본 EC2 메트릭에 보통 들어 있지 않다. Agent와 인스턴스 Role, 로그 그룹이 있어야 로그가 쌓인다.

시뮬레이터 알람은 임계값 70이다.

```text
CPU 85: ALARM
CPU 40: OK
```

실제 알람에는 평가 기간, 데이터 포인트 수, 빠진 데이터 처리가 있다.

장애를 볼 때의 순서는 정상 타깃이 있는지, EC2와 Security Group, 포트 LISTEN, 로그, 그다음 CPU·메모리·DB·지연을 같이 보는 것이다.
