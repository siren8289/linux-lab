# Part 2. 중급

## 6. TCP와 UDP

| 구분 | TCP | UDP |
|---|---|---|
| 연결 | 연결을 맺고 보냄 | 맺지 않고 데이터그램을 보냄 |
| 신뢰성 | 재전송과 순서를 프로토콜이 보장 | 프로토콜 기본 보장 없음 |
| 단위 | 바이트 스트림 | 데이터그램 |
| 예 | SSH, HTTP/1.1, HTTP/2 | DNS, VoIP. QUIC는 UDP 위에서 신뢰성을 따로 구현 |

3-way handshake는 SYN, SYN/ACK, ACK 순이다. 이후 상태는 `ESTABLISHED`다. 종료 뒤 한쪽에 `TIME_WAIT`가 남을 수 있다.

### 6-2 TCP 실습

`네트워크/tcp_server.py`가 `127.0.0.1:9000`에서 한 연결을 받고, `네트워크/tcp_client.py`가 `hello`를 보냈다.

```text
ACK:hello
Client: ('127.0.0.1', 57761)
```

이 `ACK:`는 애플리케이션이 붙인 문자열이다. TCP 헤더의 ACK 플래그가 아니다.

연결을 잠시 붙잡아 둔 `127.0.0.1:9010`의 `netstat`는 다음 세 줄이었다.

```text
tcp4  127.0.0.1.9010   127.0.0.1.57762   ESTABLISHED
tcp4  127.0.0.1.57762  127.0.0.1.9010    ESTABLISHED
tcp4  127.0.0.1.9010   *.*               LISTEN
```

LISTEN은 서버 소켓이고, ESTABLISHED 두 줄은 같은 연결의 양쪽이다. `ss -t`는 이 호스트에 없다.

### 6-3 UDP 실습

`udp_demo.py`는 9001로 `hello UDP`를 보내고 같은 프로세스의 서버 소켓이 받았다.

```text
hello UDP 127.0.0.1
```

연결을 맺는 단계는 없다.

## 7. HTTP, HTTPS, TLS

상태 코드 중 이번 실습에 실제로 나온 것은 200과, 로컬 장애의 curl 52·curl 7이다. 301, 401, 403, 404, 500, 502, 503, 504는 이번에 응답으로 받지 않았다.

`curl -I https://example.com`과 `curl -v` (00:20 KST):

- 해석된 IPv4는 `172.66.147.243`, `104.20.23.154`. 이 curl은 `IPv6: (none)`으로 IPv4에 연결했다.
- 연결 주소는 `172.66.147.243:443`.
- TLS 1.3, 암호군 `AEAD-CHACHA20-POLY1305-SHA256`.
- 인증서 CN `example.com`, 검증 성공. 발급자 `Cloudflare TLS Issuing ECC CA 3`.
- 유효 기간 2026-09-26부터 2026-12-25까지.
- ALPN으로 `h2`를 선택하고 `HTTP/2 200`을 받았다.
- `server: cloudflare`. `alt-svc`는 HTTP/3(`h3`)를 광고한다.

`openssl s_client -connect example.com:443 -servername example.com`:

- 체인 depth 3 `SSL.com TLS ECC Root CA 2022` → depth 2 Transit ECC CA → depth 1 Cloudflare TLS Issuing ECC CA 3 → depth 0 `CN=example.com`.
- `TLSv1.3`, cipher `TLS_AES_256_GCM_SHA384`.
- `Verify return code: 0 (ok)`.

같은 서버라도 클라이언트가 고른 암호군은 다를 수 있다. curl은 ChaCha20, openssl은 AES-256-GCM이었다. 둘 다 TLS 1.3이고 인증서 검증은 성공이다. 인증서가 유효하다는 말은 그 사이트의 애플리케이션이 정상이라는 뜻까지는 아니다.

## 8. 라우팅

`ip route`와 `ip route get`은 없다. `netstat -rn -f inet`과 `route -n get 8.8.8.8`을 썼다.

```text
default            172.30.1.254       UGScg    en0
127                127.0.0.1          UCS      lo0
172.30.1/24        link#5             UCS      en0
```

`8.8.8.8`로 가는 경로는 default, 게이트웨이 `172.30.1.254`, 인터페이스 `en0`, mtu 1500이다.

- `default`는 더 긴 프리픽스가 없을 때의 경로다.
- 게이트웨이가 다음 홉이다. 리눅스 출력의 `via`에 해당한다.
- `en0`가 패킷이 나가는 장치다. 리눅스의 `dev`에 해당한다.
- `172.30.1/24`가 `en0`에 직접 붙어 있으므로, 이 대역은 게이트웨이를 거치지 않는다. 가장 긴 프리픽스가 우선이다.

`traceroute -n -m 6 -w 1 1.1.1.1`의 첫 홉은 `172.30.1.254`였다. 6홉 안에는 `1.1.1.1`에 닿지 않았고 5–6홉은 시간 초과였다. 홉 제한을 6으로 둔 조회라서, 경로 전체가 끊겼다는 결론은 아니다.

## 9. NAT

NAT는 패킷의 IP를 바꾸고, NAPT/PAT는 포트까지 바꿔 여러 내부 호스트가 공인 IPv4 하나를 나누게 한다. 교재의 `192.168.1.10`과 `203.0.113.10`은 문서용 예시다.

이 Mac의 사설 주소 `172.30.1.80`에서 밖으로 나가는 변환은 게이트웨이 `172.30.1.254` 쪽에서 일어나는 형태다. `conntrack`은 없고 `sudo apt install`은 비밀번호에서 멈춘다. VM이나 이 Mac 안에서 NAT 규칙이 안 보이는 것은 교재가 말한 그대로일 수 있다. 호스트의 기존 NAT 규칙은 바꾸지 않았다.

## 10. 방화벽, SSH, VPN

방화벽의 INPUT은 이 호스트로 들어오는 패킷, OUTPUT은 나가는 패킷, FORWARD는 이 호스트를 통과하는 패킷이다.

이번 호스트에서 하지 않은 것:

- `ufw allow`, `ufw enable`. UFW가 꺼져 있으면 규칙만 추가해도 필터는 적용되지 않고, SSH 세션 중 활성화는 접속 경로를 막을 수 있다.
- `ssh-keygen`과 `ssh-copy-id`. 교재의 `student@192.168.64.10` VM이 이 환경에 없다. 홈 디렉터리에 로그인 키를 새로 만들지 않았다.
- `wireguard-tools` 설치와 `wg show`. 터널을 만들려면 양쪽 키와 피어 설정이 필요하고, 기존 라우팅을 건드리지 않으려고 설치하지 않았다.

이전에 같은 Mac에서 확인한 애플리케이션 방화벽은 꺼진 상태였다. TCP 22에는 수신 프로세스가 없었다.

바인딩 주소와 방화벽은 다른 층이다. Docker가 `127.0.0.1:8080`만 듣고 있으면, 방화벽에서 8080을 열어도 다른 장비에서는 그 포트로 들어오지 않는다.
