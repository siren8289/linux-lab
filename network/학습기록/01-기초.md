# Part 1. 기초

## 3. OSI 7계층과 TCP/IP

OSI는 참조 모델이다. 인터넷에서 실제로 패킷을 설명하는 말은 TCP/IP 4계층에 더 가깝다. TLS는 계층 하나에 딱 떨어지지 않고, 전송 계층 위에서 응용 데이터를 보호한다.

| TCP/IP | OSI | 이번 실습에서 만난 예 |
|---|---|---|
| Application | 5–7 | HTTP, DNS, SSH |
| Transport | 4 | TCP 9000, UDP 9001 |
| Internet | 3 | `172.30.1.80`, `8.8.8.8`로 가는 경로 |
| Link | 1–2 | `en0` MAC, ARP 캐시 |

캡슐화는 보내는 쪽에서 HTTP 데이터 앞에 TCP 헤더, IP 헤더, Ethernet 헤더를 붙이고, 받는 쪽에서 역순으로 벗긴다. Ethernet 프레임 끝에는 FCS가 있다. HTTPS면 TCP와 HTTP 사이에 TLS 레코드가 들어간다.

### 실습 1 — 인터페이스

교재 명령 `ip -br addr`, `ip -d link show`, `ip -s link`는 `command not found`였다. 같은 정보는 `ifconfig`와 `netstat -ib`로 읽었다.

| 인터페이스 | 역할 | 이번 값 |
|---|---|---|
| `lo0` | 자기 자신과 통신하는 루프백 | `127.0.0.1`, netmask `0xff000000` 즉 `/8`, mtu 16384 |
| `en0` | 올라와 있는 무선 인터페이스 | `172.30.1.80/24`, broadcast `172.30.1.255`, MAC `f6:e8:2f:bb:25:70`, mtu 1500, status active |

`en0` 누적 통계는 수신 약 20,041,592패킷 / 약 21.9GB, 송신 약 7,981,341패킷 / 약 3.3GB다. 교재 예시의 `enp0s1 192.168.64.10/24`는 이 Mac의 주소가 아니다.

검증: 루프백과 실제 인터페이스를 나눌 수 있다. 실제 통신에 쓰는 IPv4는 `172.30.1.80/24`다.

돌아가는 Ubuntu 컨테이너 `festive_joliot`(`ubuntu:24.04`)에는 `ip`가 설치되어 있지 않다. 컨테이너 안에 패키지를 설치하지는 않았다.

## 4. IPv4, CIDR, 서브넷

IPv4는 32비트다. `192.168.10.25/24`는 주소 `192.168.10.25`, 앞 24비트가 네트워크라는 뜻이다.

호스트 비트가 h개면 전체 주소는 \(2^h\)개다. 일반 서브넷의 호스트 주소 수는 네트워크 주소와 브로드캐스트를 뺀 \(2^h - 2\)다. `/31`과 `/32`는 이 표대로 빼지 않는다. 클라우드 서브넷은 여기서 또 몇 개를 예약한다.

Python 표준 라이브러리로 계산했다.

| CIDR | 네트워크 | 마스크 | 브로드캐스트 | 전체 | 호스트 범위 |
|---|---|---|---|---|---|
| `192.168.10.25/24` | `192.168.10.0` | `255.255.255.0` | `192.168.10.255` | 256 | `1`–`254` |
| `192.168.10.25/27` | `192.168.10.0` | `255.255.255.224` | `192.168.10.31` | 32 | `1`–`30` |
| `192.168.10.130/24` | `192.168.10.0` | `255.255.255.0` | `192.168.10.255` | 256 | `1`–`254` |
| `192.168.10.130/25` | `192.168.10.128` | `255.255.255.128` | `192.168.10.255` | 128 | `129`–`254` |
| `192.168.10.130/26` | `192.168.10.128` | `255.255.255.192` | `192.168.10.191` | 64 | `129`–`190` |
| `192.168.10.130/27` | `192.168.10.128` | `255.255.255.224` | `192.168.10.159` | 32 | `129`–`158` |
| `192.168.10.130/28` | `192.168.10.128` | `255.255.255.240` | `192.168.10.143` | 16 | `129`–`142` |

`192.168.10.130/26`을 비트로 보면 마지막 옥텟 `130`은 `10000010`이다. `/26` 마스크의 마지막 옥텟은 `11000000`(192)이라 네트워크는 `10000000`(128)이다. 브로드캐스트는 호스트 비트 6개를 모두 1로 둔 `10111111`(191)이다. 그래서 130은 `192.168.10.128/26`에 들어간다.

## 5. ARP, DHCP, DNS

| 기술 | 하는 일 | 이번 관찰 |
|---|---|---|
| ARP | 같은 링크에서 IPv4를 MAC으로 바꿈 | `arp -an`. 게이트웨이 `172.30.1.254`의 MAC은 `c:96:cd:4a:16:35` |
| DHCP | 주소, 게이트웨이, DNS를 빌려 줌 | 재임대는 하지 않음. 이미 받은 값은 주소 `172.30.1.80/24`, 게이트웨이 `172.30.1.254`, DNS `168.126.63.1`, `168.126.63.2` |
| DNS | 이름을 레코드로 바꿈 | `dig example.com` |

DORA는 Discover, Offer, Request, ACK다. 임대를 강제로 다시 받으면 주소가 바뀌며 기존 접속이 끊길 수 있어 조회만 했다. `networkctl`과 `resolvectl`은 이 Mac에 없다. DNS 서버 목록은 `scutil --dns`로 봤다.

`dig example.com A` (2026-10-29 00:19 KST):

```text
;; QUESTION SECTION:
;example.com.                   IN      A

;; ANSWER SECTION:
example.com.            3       IN      A       172.66.147.243
example.com.            3       IN      A       104.20.23.154

;; SERVER: 168.126.63.1#53(168.126.63.1)
;; Query time: 133 msec
```

- `ANSWER SECTION`이 있고 타입은 `A`다.
- TTL로 보이는 `3`은 그 순간 리졸버가 알려 준 남은 시간이다. 권한 서버의 원래 TTL 전체는 아니다.
- `dig +short example.com AAAA`는 `2606:4700:10::ac42:93f3`, `2606:4700:10::6814:179a`를 줬다.
- `dig @1.1.1.1 example.com A`도 같은 두 IPv4를 줬다.

이웃 항목 중 `172.30.1.17`과 `172.30.1.54`는 `(incomplete)`였다. 질의는 나갔지만 응답 MAC이 캐시에 없는 상태다.
