# 3. 심화 — 권한, 로그, 장애

## 비루트

```text
docker run --rm study-api:1.0 id
uid=10001(appuser) gid=10001(appuser) groups=10001(appuser)
```

이미지의 `USER`가 실행 사용자가 된다. 컨테이너 안의 root와 Mac의 root는 같은 계정이 아니고, 여기서는 앱 프로세스가 root도 아니다.

## 읽기 전용 루트와 capability

```text
docker run --rm --read-only --cap-drop ALL \
  --security-opt no-new-privileges:true \
  alpine:3.20 sh -c 'id; touch /blocked.txt'
```

```text
uid=0(root) gid=0(root) groups=0(root),1(bin),2(daemon),...
touch: /blocked.txt: Read-only file system
readonly_root_exit=1
```

`id`와 셸은 그대로 실행됐다. `--cap-drop ALL`이 모든 시스템 호출을 막지는 않는다. 이번 실패의 직접 원인은 capability가 아니라 읽기 전용 파일시스템이다.

Docker 소켓 `/var/run/docker.sock`은 엔진을 제어하는 권한이다. 이번 학습에서는 어떤 컨테이너에도 붙이지 않았다.

## 로그와 상태

Compose 헬스 체크와 curl이 `docker compose logs`에 액세스 로그로 남았다. `BaseHTTPRequestHandler`가 stderr에 한 줄씩 쓰기 때문이다.

상태 확인에 쓴 값:

```text
docker inspect --format 'Status={{.State.Status}} OOM={{.State.OOMKilled}} Exit={{.State.ExitCode}}'
```

정상이던 `fundamentals-api-1`은 `Status=running OOM=false Exit=0 Health=healthy`였다.

`docker stats --no-stream resource-lab`는 제한 128MiB 안에서 532KiB를 쓰는 것만 보여 주고 끝났다.

## 일부러 만든 장애

| 상황 | 관찰 |
|---|---|
| 포트 미공개 | curl exit 7, connection refused |
| 8080 중복 | exit 125, `port is already allocated`. kind는 유지 |
| 앱이 듣기 전 게시 포트 | curl exit 52, `Empty reply from server`. 이후 200 |
| 아무도 없는 8099 | curl exit 7 |
| 다른 Docker 네트워크의 이름 | `ping: bad address 'server-a'` |
| 이름은 되는데 포트가 닫힘 | DNS는 172.25.0.2, wget은 connection refused |
| 읽기 전용 마운트·루트 | `Read-only file system` |
| 메모리 32MiB | 아래 OOM |

OOM은 32MiB 제한과 swap 없음으로 64MiB `bytearray`를 만들게 했다.

```text
Status=exited OOM=true Exit=137 Error=
```

표준 출력 로그는 비어 있다. 할당이 끝나 출력하기 전에 커널이 프로세스를 죽였다. 종료 코드 137은 128+9, 즉 SIGKILL이다. 원인 후보는 앱 버그보다 메모리 제한이다. `docker inspect`의 `OOMKilled`와 `docker stats`의 LIMIT를 같이 본다.

분석 순서는 컨테이너를 바로 지우기 전에 `docker ps -a`, `docker logs`, `docker inspect`의 State, `docker port`, 네트워크, 호스트의 `lsof`다. 8080은 이 순서로 kind임을 확인했다.
