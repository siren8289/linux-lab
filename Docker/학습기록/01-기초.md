## 컨테이너와 VM

같은 시각에 커널을 비교했다.

```text
[host]      Darwin 25.6.0 arm64
[container] Linux 6.12.76-linuxkit aarch64
```

컨테이너 프로세스는 별도의 Guest OS를 부팅하지 않는다. 다만 이 Mac에서는 그 프로세스가 Docker Desktop Linux VM 안에서 돈다. VM이 하드웨어를 격리하고, 그 안의 컨테이너들이 linuxkit 커널을 공유한다.

## PID Namespace

```text
docker run --rm alpine:3.20 sh -c 'echo "PID=$$"; ps; echo COMM=$(cat /proc/1/comm)'
```

```text
PID=1
PID   USER     TIME  COMMAND
    1 root      0:00 sh -c echo "PID=$$"; ps; echo COMM=$(cat /proc/1/comm)
    7 root      0:00 ps
COMM=sh
```

이 실험의 PID 1은 `sleep`이 아니라 셸이다. `sh -c`가 컨테이너의 1번 프로세스이기 때문이다. PoC 1에서는 `sleep`을 PID 1로 두고 `/proc/1/comm`이 `sleep`인지 확인했다.

컨테이너 안의 1번과 Mac의 프로세스 번호는 다른 공간이다. Mac에는 그 프로세스의 PID가 그대로 1로 보이지 않는다.

## UTS Namespace

```text
docker run --rm --hostname study-container alpine:3.20 hostname
study-container
hostname
jeong-yelim-ui-MacBook-Neo.local
```

`--hostname`은 컨테이너의 UTS Namespace만 바꾼다. Mac의 호스트 이름은 그대로다.

## Network Namespace

alpine 컨테이너의 eth0는 `172.17.0.3/16`였다. `/proc/net/route`의 기본 게이트웨이 `010011AC`는 리틀 엔디언으로 `172.17.0.1`이다. 목적지 `000011AC`와 마스크 `0000FFFF`는 `172.17.0.0/16`이다. 이건 Mac의 `en0`(172.30.1.80/24)이 아니다.

`/etc/resolv.conf`는 Docker Engine이 만들었고 nameserver는 `192.168.65.7`이다. Docker Desktop이 Linux VM 안에 두는 해석기다.

`ip addr`도 동작했다. 예전에 살펴본 `festive_joliot`(ubuntu:24.04)에는 `ip`가 없었지만, 이번 alpine 이미지에는 있다. 그 컨테이너에는 패키지를 설치하지 않았다.

## cgroup

메모리 128MiB:

```text
docker run --rm --memory=128m alpine:3.20 cat /sys/fs/cgroup/memory.max
134217728
```

CPU 0.5:

```text
docker run --rm --cpus=0.5 alpine:3.20 cat /sys/fs/cgroup/cpu.max
50000 100000
```

100000µs 주기마다 50000µs다. `할당량 * 2 = 주기`라서 0.5 CPU다.

`resource-lab`를 같은 제한으로 띄운 뒤 `docker stats --no-stream` 결과는 `532KiB / 128MiB`, CPU `0.00%`, PIDS 1이었다. `HostConfig.Memory`는 `134217728`, `HostConfig.NanoCpus`는 `500000000`(0.5 × 10^9)이었다. 확인 후 컨테이너는 삭제했다.

Namespace가 보이는 세계를 나누고, cgroup이 그 프로세스 집합이 쓸 수 있는 CPU와 메모리를 제한한다.
