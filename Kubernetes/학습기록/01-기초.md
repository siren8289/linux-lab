# 기초 — 개념과 클러스터 구조

기준 문서는 [v1.32 개념](https://v1-32.docs.kubernetes.io/ko/docs/concepts/)이다. 그 페이지는 정적 스냅샷이라고 적혀 있다. 이 Mac에서 만든 클러스터 버전은 그보다 높다.

## 버전

```text
Client Version: v1.37.1
Kustomize Version: v5.8.1
Server Version: v1.37.0
kind v0.33.0 go1.27.0 darwin/arm64
```

노드:

```text
k8s-lab-control-plane kubelet=v1.37.0 runtime=containerd://2.3.4 os=linux arch=arm64
```

OS 이미지는 Debian GNU/Linux 13 (trixie), 커널은 `6.12.76-linuxkit`이다. Docker 엔진은 cgroup v2였다. 노드 로그에도 `INFO: detected cgroup v2`와 `Reached target multi-user.target - Multi-User System`이 있다.

v1.37에서 확인한 차이 하나: `kubectl get endpoints`가 `v1 Endpoints is deprecated in v1.33+; use discovery.k8s.io/v1 EndpointSlice`를 출력했다. v1.32 문서의 Endpoints 설명과 같은 객체를 쓰되, 이 클러스터는 그 리소스를 폐기 예정으로 본다.

## 이미 있던 클러스터

실습 전에 읽기만 했다.

| 노드 | 역할 | 버전 | IP |
|---|---|---|---|
| `gitops-lab-control-plane` | control-plane | v1.37.0 | 172.20.0.4 |
| `gitops-lab-worker` | 워커 | v1.37.0 | 172.20.0.3 |
| `cloud-poc-control-plane` | control-plane | v1.37.0 | 172.20.0.2 |

`gitops-lab`는 control plane과 워커가 나뉜 예다. 이번 실습 클러스터 `k8s-lab`는 control-plane 노드 하나다. 워크로드도 그 노드에 올라간다. 기존 두 클러스터에는 오브젝트를 만들지 않았다. 실습이 끝난 뒤 세 노드 모두 Ready였고, `127.0.0.1:8080`은 `gitops-lab-control-plane`에 그대로 있었다.

## control plane이 하는 일

쿠버네티스는 원하는 파드 수를 선언하면 컨트롤러가 현재 상태와 맞춰 다시 만든다. `k8s-lab`를 만든 직후 `kube-system`에는 이런 파드가 있었다.

| 파드 | 역할 |
|---|---|
| `etcd-k8s-lab-control-plane` | 클러스터 상태 저장. 초기 목록에서 1/1 Running |
| `kube-apiserver-k8s-lab-control-plane` | API. `kubectl`이 붙는 대상 |
| `kube-scheduler-k8s-lab-control-plane` | 파드를 노드에 배정 |
| `kube-controller-manager-k8s-lab-control-plane` | ReplicaSet, Job 같은 컨트롤러 |
| `kube-proxy-*` | Service 주소를 노드에서 연결 |
| `kindnet-*` | 이 kind 클러스터의 CNI |
| `coredns-*` | 클러스터 DNS. 노드가 Ready되기 전에는 Pending |

시작 13초 시점에는 노드가 `NotReady`이고 apiserver readiness가 0/1인 줄도 있었다. 그 다음 `kubectl wait --for=condition=Ready node`는 `condition met`이 되었다. 워크로드는 그 뒤에 적용했다.

API 준비:

```text
Kubernetes control plane is running at https://127.0.0.1:51980
readyz check passed
```

포트 `51980`은 그 실행에서 kind가 고른 API 포트다. 실행마다 달라진다.

노드 하트비트용 Lease도 있었다.

```text
NAME                    HOLDER
k8s-lab-control-plane   k8s-lab-control-plane
```

## 컨테이너와 윈도우 문서

파드 안 프로세스는 노드의 containerd가 실행한다. 이번 이미지 `nginx:1.27-alpine`은 노드가 레지스트리에서 받았다. `kind load`는 이 멀티 아키텍처 이미지에서 content digest를 찾지 못해 실패했고, 그 방법은 쓰지 않았다. 자세한 오류는 [troubleshooting.md](troubleshooting.md)에 있다.

윈도우 노드 문서는 이 실습의 대상이 아니다. 노드 `os`는 `linux`다.

## 클러스터를 만든 방식

`kind-config.yaml`의 이름은 `k8s-lab`이고 노드는 control-plane 하나다. 호스트 포트 `8080`과 `8443`은 매핑하지 않았다. 로컬에 태그가 풀린 `kindest/node` 이미지 `a1ed56cfb0e7`를 `kindest/node:v1.37.0`으로 다시 달아 두고 그 이미지를 썼다. 새 이미지를 받지 않았다.

첫 `kind create`는 systemd가 multi-user 로그를 남기기 전에 실패했다. 이후 생성은 통과했다. 검증이 끝나면 스크립트가 `kind delete cluster --name k8s-lab`만 실행한다. 통과 실행의 마지막은 `CLEANUP_DONE previous_exit=0`이다. `kubectl config current-context`는 다시 비어 있다.
